```yaml
# Tech Design Review SOP

## When to Use
当工程师提交技术方案供团队评审时使用。

**触发关键词**：tech design、方案评审、设计评审、ADR、review design

**不适用**：
- 用户只是想讨论技术问题，而非正式评审
- 用户要求实现而非评审
- 用户问具体代码问题而非架构问题

## Prerequisites
评审前需确认：
- [ ] 技术方案文档已撰写完成
- [ ] 包含：背景、目标、技术选型、风险评估、实施计划
- [ ] 相关人员已收到评审邀请

## Review Steps

### Step 1：技术选型评估
评估：
- **扩展性**：方案是否能支撑未来 3 个月的需求？
- **成本**：开发成本 + 维护成本是否合理？
- **团队能力**：团队是否有能力实现和维护？

### Step 2：风险评估
- 列出所有识别的风险
- 每项风险是否有应对措施（ Mitigation）？
- 是否有不可接受的风险（No Mitigation）？

### Step 3：系统兼容性
- 与现有系统是否有冲突？
- 数据迁移是否需要考虑？
- 对现有服务是否有影响？

### Step 4：实施计划评估
- 时间线是否可行？
- 所需资源（人力、服务器、外部依赖）是否明确？
- 是否有回滚方案？

## Decision

评审结果必须是以下之一：

```
## ✅ Approved
可以开始实施。

## ⚠️ Request Changes
需要修改后重新评审。
修改意见：
- [ ] [具体修改意见 1]
- [ ] [具体修改意见 2]

## ❌ Rejected
否决原因：
- [ ] [具体否决原因]
```

## Follow-up（必须执行）

评审完成后：
1. 将评审结果同步到技术方案文档
2. 在 #tech-design 频道通知结果
3. 如有修改意见，指定复审日期
```
