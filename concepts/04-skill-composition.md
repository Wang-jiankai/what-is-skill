# 04 | Skill 的编排与组合

## 🎯 学习目标

- 理解多个 Skill 如何协同工作
- 掌握 Skill 的触发优先级设计
- 学会设计 Skill 之间的依赖关系

---

## 📖 概念讲解

### 为什么要组合 Skill？

现实任务往往需要多个领域的知识：

```
用户需求：帮我把这个功能上线到生产环境
需要的 Skill：
  ├── code-review（审查代码）
  ├── test-runner（运行测试）
  ├── deployment（部署流程）
  └── monitoring（检查监控）
```

一个 Skill 装不下所有知识，就需要**编排与组合**。

### Skill 之间的两种关系

**并行关系**：
多个 Skill 都相关，AI 自主决定使用哪些。

```
用户：帮我做一个用户登录功能

可能触发的 Skill：
  ├── api-design（API 怎么设计）
  ├── database-schema（数据库怎么建）
  └── auth-security（认证安全注意点）

AI 根据需求自主选择需要的 Skill
```

**串行关系**：
前一个 Skill 的输出，是后一个的输入。

```
用户：帮我做一个代码审查

Skill 链：
  code-review（审查代码）
    ↓ 输出：审查报告 + 需要修改的代码
  pr-summarize（生成 PR 摘要）
    ↓ 输入：审查报告
    ↓ 输出：给 reviewer 的摘要
  notification（发送通知）
    ↓ 输入：摘要
    ↓ 输出：Slack 消息
```

### 触发优先级

当多个 Skill 都可能匹配时，AI 会选择最相关的一个。但可以通过命名和描述来暗示优先级。

```yaml
# 高优先级 Skill（更具体的场景）
name: api-design-rest
description: RESTful API 设计规范。当用户说 "design API"、"REST"、"接口设计" 时优先触发。

# 低优先级 Skill（更通用的场景）
name: code-design
description: 通用代码设计原则。
```

### 避免 Skill 冲突

如果两个 Skill 对同一个任务有不同要求，AI 会困惑。

**❌ 冲突示例**：
```
Skill A：
  ## Steps
  1. 先写测试
  2. 再写代码

Skill B：
  ## Steps
  1. 先写代码
  2. 再写测试
```

**✅ 避免冲突**：
明确每个 Skill 的边界，或者在一个 Skill 内部描述不同情况：

```yaml
## Steps

### TDD 模式（当用户说 "TDD" 或 "测试驱动" 时）
1. 先写测试
2. 再写代码

### 直接开发模式（默认）
1. 先写代码
2. 再补测试
```

---

## 💡 生活中的类比

Skill 组合就像**餐厅后厨的分工单**：

- 每个厨师（Skill）有自己负责的菜系
- 大厨（AI）根据客人点的菜（用户需求）决定叫谁出场
- 有的人负责切菜（并行），有的人负责上菜前的摆盘（串行）
- 分工明确，互不冲突，各司其职

---

## 📝 章节回顾

**记住：**

1. **并行**：多个 Skill 都相关，AI 自主选择
2. **串行**：前一个输出是后一个输入，形成链
3. **避免冲突**：边界要清晰，同一件事只有一个正确答案
